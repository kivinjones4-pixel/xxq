# spec 自动更新与生成

## 定位与目录

spec 是功能/迭代级的可执行规范：明确“这次要干什么、哪些不做、如何实现与验证、什么算完成”。一个独立交付需求一个目录，每个目录默认一份 `spec.md`，不按前端、后端等技术层拆散同一需求。

先读取项目 `AGENTS.md`、现有目录和相关需求来源。本仓库沿用现有 `specs/` 与 `skills/` 命名；不要另建平行的 `spec/` 根目录。示例结构（不是已创建的功能）：

```text
specs/
  000-frontend-init-feature/
    spec.md
  001-meter-import-feature/
    spec.md
```

目录名使用至少三位递增编号和小写 kebab-case 功能名。新目录先扫描现有编号，无编号目录时从 `000` 开始，否则最大编号加一；创建前再次检查冲突，不覆盖其他需求。遵循用户明确指定的名称，已有目录不因排序或更名意向自动重新编号。

项目根部既有 proposal/design/task/spec/reference 是背景基线，保留并引用；它们不替代本次功能规范，也不因新增技能而自动搬迁。复杂功能可按需在同目录拆出 proposal.md、design.md、task.md 或证据文件，spec.md 保持入口和验收依据，各信息只维护一处。

## 生成流程

1. 识别本次交付目标、使用者和可观察结果，查找是否已有对应功能目录。相同目标的补充或修复更新原目录，独立交付的新需求另建目录；不为每次对话重复建目录。
2. 从原始需求、项目基线、代码与已有决策提取事实，区分明确要求、采用的设计假设和未决事项。仅请求生成技能时不替用户创建真实功能迭代。
3. 使用 [规范模板](assets/spec-template.md) 生成 `spec.md`，替换模板说明，不保留空占位符。按实际复杂度压缩章节，但保留目标、范围、验收、任务、验证和完成条件。
4. 为需求、验收场景和任务分配目录内稳定 ID，例如 R-01、AC-01、T-01；引用时带目录名避免跨需求混淆。每项必需需求至少有一个可验证场景和对应任务。
5. 验收场景写明 Given/When/Then 或输入/操作/预期，覆盖正常路径、与该改动有关的失败和边界。不能只写“页面正常”“性能良好”；只有有依据时才设定数值指标。
6. 明确接口、数据、依赖、设计决策、任务顺序与验证方法。不存在的命令不写成可运行命令；尚无工程时写明验证步骤及需要补齐的脚本。
7. 关键合同不明时列出问题及阻塞任务，可继续不依赖它的规范和实现。草案可交付，不能因时间经过将待决问题视为批准。

## SDD 自动更新规则

“自动更新”指本次工作中识别相关变化并同步文件，不代表后台监控、定时执行或自动发布。

| 变化 | 更新内容 |
| --- | --- |
| 用户增加/修改范围 | 目标、范围、需求、验收与受影响任务；记录变更原因 |
| 采用新的实现方案 | 设计、接口/数据、依赖、风险和验证；行为变化同时更新验收 |
| 发现实现偏离规范 | 先判断缺陷还是用户明确变更；修复缺陷，不能降低验收以迁就代码 |
| 验证失败或未运行 | 记录真实结果、影响、后续任务，保持相关任务未完成 |
| 验证通过 | 关联实际命令/步骤、结果和证据，再更新任务与状态 |

行为变化遵循“先更新规范，再实现，再验证，再记录证据”。更新已有文档时保留稳定 ID、有效证据、用户手工内容和决策原因，不整体覆盖历史；旧证据受影响时标记失效并补充回归任务。只同步受影响范围及相关背景基线，不重写无关迭代。

## 状态与完成判据

- 草案：需求正在整理，仍有影响范围或验收的待决事项。
- 就绪：目标、范围、必需场景、依赖与任务已明确，相关阻塞已解决；这是文档成熟度，不表示用户做过额外审批。
- 实施中：已有实施动作，必需验收尚未全部满足。
- 完成：范围内必需任务完成，验收逐项通过且有证据，相关回归通过，无未解决的交付阻塞，文档与实现一致。
- 变更后重开：已完成内容受新变更影响时回到实施中，保留原完成记录并注明失效场景。

仅写完 spec、仅返回任务 ID、仅提交代码、未运行测试或只通过不相关检查，都不能标记功能完成。与本次范围无关的项目级任务无需为了完成本迭代而全部完成。

## 输出与自检

输出创建/更新的目录、目标、主要验收、状态与未决事项；检查本地链接、ID 映射、任务状态与证据一致性。优先运行项目已有校验脚本，不生成只匹配措辞的测试或虚构 CLI 命令。本技能不安装 OpenSpec、不自动提交或部署。
